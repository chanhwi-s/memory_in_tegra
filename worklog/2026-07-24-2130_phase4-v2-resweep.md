## Key decisions & rationale
- **`is_anchor`/size-based matching instead of label-based, for the sanity gate.** Reading
  the checked-in v1 `results/test_points_config.csv`, both `sym_0` and `sym_1` rows show
  `k0_bytes=k1_bytes=917504` — the first run's `gen_test_points.py` matched Phase 3's
  `test_point_id` strings via `"90" in tpid`, and neither `sym_0` nor `sym_1` contains "90",
  so both fell through to the same `onset` size. This means v1 never actually measured
  Phase 2's `ninety_pct` (786432 B) point. v2 fixes the root cause (reads Phase 2's roofline
  sizes directly, no substring matching) and documents the discrepancy rather than silently
  re-using the mislabeled baseline.
- **Regime-aware config consumption is defensive/best-guess**, since Phase 3 v2's exact
  `configs_for_phase4` shape isn't finalized yet (a different session owns it). Implemented
  detection for a `regime`/`size_regime` field with a nearest-regime fallback; if Phase 3 v2
  ships a different shape, `gen_test_points.py` will need a follow-up patch — flagged in
  README and here for the next session.
- **Search trial count = 3 during the block-saturation search, 10 for the final measured
  cell** — matches `phase2_bench`'s existing convention (search only needs the argmax, not
  publication-quality numbers).
- **Did not run `scripts/run.sh` or attempt to compile `phase4_bench.cu`** — this
  environment has no CUDA toolchain or Jetson device. Per the user's direction this session,
  a separate person will upload both this Phase 4 v2 work and the parallel Phase 3 v2 work
  to the actual Jetson server and re-run Phases 1-4 there.
