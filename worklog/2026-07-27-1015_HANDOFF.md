## 0. What this project is (1 paragraph)

Characterizing two GPU-optimization mechanisms on the Orin iGPU (unified memory, 16 SMs, sm_87):
**green context** (partition SMs between two concurrent kernels → isolates L1 + scheduling) and
**zero copy** (route a kernel's reads around GPU cache, straight to DRAM). Workload is a
memory-bound `C = A + B` float kernel. Axes are isolated one at a time across 4 phases (see
`OVERVIEW.md`). Hardware: NVIDIA Jetson AGX Orin 64GB, CUDA 13.2, MAXN + jetson_clocks, GPU locked
1.3 GHz. Measured DRAM peak ≈ **177 GB/s**.

## 2. Trustworthy findings (safe to build on)

1. **Bottleneck is memory/cache, not SM.** Phase 2 reuse overlay: two concurrent kernels DO get a
   cache boost when reuse>1 — at combined footprint 2MB, aggregate rises 191 (N=1) → **322 GB/s
   (N=32)**, well above DRAM peak. Collapses onto DRAM peak once combined footprint ≥ ~8MB. Green
   context (SM partitioning) never recovers the loss → SM contention is not the driver.

2. **Effective cache boundary ≈ 2MB read footprint** (Phase 1 measured: L2-resident ≤1MB, cache-
   served ≤2MB, DRAM-bound ≥4MB) — much smaller than nominal (L2 4MB + SLC 4MB). Document this
   nominal-vs-measured discrepancy; OVERVIEW §0 still assumes 4MB/8MB boundaries.

3. **Cache boundary is on COMBINED footprint → per-kernel peak scales as 1/kernel-count.** Single
   kernel peaks at per-kernel 1MB (footprint 2MB); two kernels peak at per-kernel **512KB** (combined
   2MB). Phase 2 (x-axis = combined footprint) and Phase 3 (x-axis = per-kernel size) are the SAME
   data — their peaks differ only by the ×4 axis definition (2 kernels × 2 buffers). Phase 3 shared
   reproduces Phase 2 within noise.

4. **Green context helps only when per-SM working set fits L1 AND reuse exists.** Phase 3 reuse
   overlay: at the tiny L1-resident size (32KB), green LOSES at N=1 but WINS from reuse≥4, margin
   growing with reuse (+2% N=4 → +10% N=16 → +9% N=32). This is the first direct evidence of green's
   intended mechanism (stabilizing L1 inter-launch reuse; shared mode reshuffles blocks across SMs
   between launches and loses L1 residency). At N=1 (Phase 3 main sweep) green wins only 2/29 points,
   marginal. Absolute throughput at 32KB is low (~12–24 GB/s, latency-bound) — mechanism proof, not a
   high-perf regime.

5. **Zero-copy DIRECTION only (magnitudes untrusted, see §4):** helps at small asymmetric K1
   (L2/SLC-contention regime), benefit decays to ~0 as K1 grows DRAM-bound.

## 4. KNOWN BROKEN — Phase 4 (fix this first)

Phase 4's zero-copy deltas are **not trustworthy**:
- Sanity gate FAILS: re-swept cached aggregate is LOWER than the v1 baseline at `asym_2` (N≥16) and
  `sym_1` (N≥2..32). `findings.json` itself says "do not trust the zero-copy delta."
- **17 of 22 cells did not reach the block-count plateau** (`results/chosen_blocks.csv`,
  `plateau_reached=0`); chosen `blocks_k1` is pinned at the search cap **1024**.
- Headline zc benefit is unstable run-to-run (+15.8% → +7.4% at `asym_00`) — classic under-saturation.

**Root cause:** the in-context block-saturation search in `experiments/04_zero_copy/src/phase4_bench.cu`
is too narrow. Fix (not yet applied):
- `clampBlocks` cap 1024 → **8192**
- `kSearchMultipliers = {1,2,4,8}` → add **16** (and it must actually exceed the plateau, not hit the cap)
- `kSearchTrials = 3` → **10**
Then rerun Phase 4 until the sanity gate passes and `plateau_reached=1` for (nearly) all cells.
Only then are the compute-bound-vs-memory-bound conclusions and the −10% at `asym_2` believable.
