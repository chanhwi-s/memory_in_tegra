## Key decisions & rationale
- **Large kernel = K1, always.** Phase 2's asymmetric mode defines K0 fixed / K1 grown, so
  K1 is the natural "large/streaming" kernel there; for symmetric mode (equal sizes) there's
  no principled choice, so K1 was picked by fixed convention to keep one code path. Documented
  in README.
- **Green context implemented now but unverified.** Used the CUDA 12.4+ driver API
  (`cuDeviceGetDevResource` / `cuDevSmResourceSplitByCount` / `cuDevResourceGenerateDesc` /
  `cuGreenCtxCreate` / `cuGreenCtxStreamCreate`) per `prompts/03_green_context.md`'s
  implementation notes, guarded by `#if CUDA_VERSION >= 12040` so it compiles on older
  toolkits (stubs out and skips `config=green` rows with a stderr warning instead of faking
  partitioning). Could not compile-test on this machine (no CUDA toolkit here, same
  limitation noted in Phase 1's README) — **must be validated on-device before trusting any
  green-context numbers.**
- **L2 hit-rate profiling is a separate step (`profile_l2.sh`), not inline in the sweep.**
  Nsight Compute (`ncu`) replay overhead makes per-cell profiling impractical across the
  full reuse_N sweep; one profiled (cached, zerocopy) pair per test point at reuse_N=1 is
  broadcast across all rows for that test point in `phase4_results.csv`. Rationale spelled
  out in README ("L2 hit-rate columns are broadcast, not per-row").
- **`gen_test_points.py` matches Phase 3's `configs_for_phase4` test_point_id strings to
  Phase 2's size fields by naming convention** (`sym`/`asym` prefix, `"90"` substring for
  the 90%-below point). This is fragile — if Phase 3's actual id scheme differs, entries
  will be skipped with a warning rather than mis-sized. Flag this when Phase 3 is
  implemented; may need to align naming or have Phase 3 emit sizes directly.
